# Sovereign Memory Protocol (SMP)

*🇬🇧 [English](README.md) · 🇩🇪 [Deutsch](README.de.md) · 🇪🇸 [Español](README.es.md) · 🇷🇺 **Русский***

**Постоянная, самостоятельно размещаемая, проверяемая долговременная память для LLM-агентов — спецификация + эталонный движок.**

*Каждое утверждение в этом документе описывает состояние на его дату (последняя редакция: 2026-09-28). Утверждения об области исследований и об этой системе пересматриваются, когда меняются данные.*

## Аннотация

LLM-агенты теряют свою историю в конце каждого контекстного окна. SMP хранит память агента в простых текстовых файлах под контролем версий на оборудовании, принадлежащем пользователю, и снова делает её доступной на каждом ходе диалога. Извлечение работает по принципу *push, а не pull*: прежде чем модель ответит, хук автоматически вставляет в контекст релевантную память — модели никогда не нужно решать, искать ли. Ночной проход консолидации сжимает день и понижает приоритет неиспользуемого материала для будущих извлечений (сырые журналы сохраняются); хеш-цепочка по консолидированным слоям ежедневно зеркалируется на удалённый git-хост. Ограничения перечислены ниже рядом с измерениями.

## Что отличается

Системы памяти для LLM-агентов обычно либо заранее загружают фиксированный профиль в начале сессии, либо предоставляют извлечение как инструмент, который модель может вызвать (pull). SMP выполняет извлечение вне модели, на каждом ходе: хук на стороне клиента берёт входящее сообщение как запрос, извлекает подходящую память через детерминированный лексический слой и плотный (dense) ретривер и добавляет найденное перед контекстом до начала генерации. Модель не формулирует запрос и не решает, искать ли; она видит вставленные фрагменты, но не инициирует извлечение. Извлечение зависит от сигнала, а не от намерения (*cue-dependent rather than intent-dependent*): входящее сообщение — это сигнал для извлечения, а не цель извлечения. Вставка на каждом ходе без вызова инструмента сама по себе не уникальна для SMP — например, интеграции mem0 тоже выполняют поиск на каждом ходе и добавляют результаты в начало.

Насколько нам известно, по состоянию на сентябрь 2026 года ни одна другая публично задокументированная система не сочетает (а) вставку памяти на каждом ходе, запускаемую вне модели, с детерминированным лексическим слоем гарантии рядом с плотным извлечением, (б) ночную консолидацию с намеренным забыванием поверх читаемого человеком хранилища под контролем версий, (в) регулярные аудиты консолидированной записи по сырым журналам и (г) цепочку целостности по консолидированным слоям — при непрерывной работе с одним агентом с весны 2026 года и с измеренным качеством извлечения (см. ниже). Мы приветствуем контрпримеры.

## Как это работает

| Этап | Что происходит | Механизм |
|---|---|---|
| **Запись** | Каждый ход диалога записывается в простые текстовые файлы памяти (git-репозиторий). | Markdown + git; читаемо и редактируемо человеком. |
| **Извлечение (push)** | При каждом сообщении пользователя до генерации запускаются два ретривера; их результаты вставляются в промпт. | (1) *Sentry*: лексический индекс триггеров — детерминированный, гарантирует доступность назначенных ключевых документов. (2) *ESV*: плотное извлечение (bge-m3, 1024 изм., локально), объединённое с лексической оценкой, с порогом, с переупорядочиванием в пользу первоисточников перед их пересказами. |
| **Консолидация** | Ночью LLM-проход сжимает день в дневные, недельные и месячные слои; неиспользуемое понижается в приоритете, сырые журналы сохраняются. | Плановая консолидация («REM»), сила, зависящая от использования (*Engram*, v0.3, на проверке). |
| **Свидетельство** | Каждый консолидированный слой связывается хеш-цепочкой; цепочка ежедневно отправляется на удалённый git-хост. В эталонной установке сам агент имеет право записи на этот хост, поэтому сегодня это журналируемый, а не независимый свидетель (см. Ограничения). | Цепочка SHA-256 + git-remote. Отдельно: начало репозитория протокола закреплено в блоке Bitcoin 956116 (2026-06-30). |
| **Аудит** | Цитаты в консолидированной памяти проверяются по сырому журналу; сообщается о расхождениях и отсутствующих записях. | Плановые аудиты, только отчёты — решает человек. |

«Push» не значит «без поиска»: технически это извлечение, как в любой RAG-системе. Разница в том, *кто его запускает* — клиент на каждом ходе, а не модель по требованию.

## Измерения (эталонная установка, 2026-09-28)

- **Качество извлечения** — эталонный набор из 74 запросов с подтверждёнными людьми целевыми документами, взятых из собственной истории диалогов одного агента; 59 838 фрагментов памяти (разбиение: `engine/esv_index.py`); только плотный ретривер (без лексического Sentry): Recall@1 **37,8 %**, @3 **54,1 %**, @10 **71,6 %**, @100 **93,2 %**; медианный ранг первого правильного документа: **3**.
- **Задержка** — лексический Sentry: 10–86 мс на сообщение; плотное извлечение: ~0,6 с на сообщение (процессор ноутбука 2019 года + встроенная графика, всё локально).
- **Целостность консолидации** — цепочка (249 дневных и 74 недельных звена на 2026-09-24) проверяется ежедневно с июля 2026 года.

Метод и скрипты: `engine/` и [spec/whitepaper.ru.md](spec/whitepaper.ru.md). Результаты получены на одной установке и в одной предметной области, с небольшим эталонным набором; это базовая линия, а не бенчмарк.

## Что SMP гарантирует — и чего нет

- ✔ Он может *извлечь* только то, что действительно есть в записи: извлечённые фрагменты — дословные части сохранённых файлов.
- ✔ Последующие изменения консолидированной памяти *обнаружимы* (целостность).
- ✘ Хеш-цепочка доказывает целостность, **а не правильность**. Если консолидация записывает в запись что-то ложное, цепочка верно сохраняет ложную запись. Мы наблюдали именно это (LLM, дописывающая обрезанные цитаты). Контрмеры (видимые метки обрезки, буферы по размеру содержимого, проверка цитат по сырому источнику) запланированы для v0.5; в эталонной установке первые две работают постоянно, проверка цитат — еженедельно.
- ✘ То, что модель *говорит* о правильно извлечённом воспоминании, — обычная генерация и всё ещё может быть ошибочным.
- ✘ Свидетель независим лишь настолько, насколько независим его хост. В эталонной установке сам агент имеет право записи в (приватный) репозиторий памяти. Запланировано: свидетель, которого агент не может переписать, — блоки цепочки копируются в хранилище однократной записи (object lock в режиме compliance), так что уже засвидетельствованные блоки никто не может изменить, включая оператора.
- ✘ Формальной модели угроз пока нет (допущения о компрометации хоста, независимости свидетеля и доверии к оператору изложены лишь неформально в этом списке).
- ✘ Момент рассуждения не приватен: если используется размещённая у провайдера модель, извлечённый контекст отправляется этому провайдеру. Суверенно только хранение.

## Связанные работы

SMP — не первая система памяти для LLM-агентов, а проактивная вставка памяти — активная тема исследований (например, *Remember When It Matters: Proactive Memory Agent for Long-Horizon Agents*, arXiv:2607.08716; *TriggerBench: Investigating Prospective Memory for Large Language Models*, arXiv:2606.23459). **MemGPT/Letta** позволяет модели самой управлять памятью через вызовы инструментов (pull). **mem0** и **Zep** предоставляют слои памяти, которые извлекают факты или строят (темпоральные) графы знаний; интеграции mem0 могут искать на каждом ходе и добавлять результаты без вызова инструмента, то есть тоже вставляют автоматически. *Proactive Memory Agent* идёт в другом направлении: отдельный агент памяти решает, вставлять ли напоминание вообще, и авторы сообщают, что выборочная вставка работает лучше постоянной — результат, который напрямую касается решения SMP вставлять память на каждом ходе. **ChatGPT memory** хранит факты о пользователе на стороне провайдера. Проектные решения SMP отличаются сочетанием, а не отдельным компонентом: хранение в виде читаемых человеком файлов под контролем версий пользователя; детерминированный лексический слой рядом с плотным извлечением; консолидация с намеренным забыванием; цепочка целостности по консолидированным слоям (сейчас журналируемый, а не независимый свидетель); и аудиты консолидированной записи по сырым журналам.
